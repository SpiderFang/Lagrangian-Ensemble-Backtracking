# 四區五站正式運算與單站試跑的效能改善

本計畫目前依 2026-09-15 使用者裁決，直接服務未來各區的正式完整研究母體；不再以新舊版本倍率 A/B 比較或單站短時試跑作為本工作線目標。正式母體的情境數、成員數與敏感度矩陣仍須由版本化研究設計及科學驗證決定，不能藉效能改善自行縮減，也不能把歷史工作量硬編碼成未來母體。

## 第一工作線：正式運算總工期

評估單位為固定研究工作量從準備到產出可驗證成果所經過的時間。不得把各分片內部時間相加當作整機經過時間，也不得以提早遇到資料缺口的粒子代表完整 30 天成本。

| 順序 | 改善項目 | 目的與驗收 |
|---|---|---|
| 1 | 同一執行程序接續處理多個分片 | 單次開啟同一 run 的 controller，重用已驗證的設定、流場管理器、網格及月份資料窗；分片鎖、來源綁定、checkpoint 與各粒子亂數仍獨立。與逐片啟動的結果及續跑結果一致。 |
| 2 | 重用步首速度作為 RK4 第一階段樣本 | 只在明確支援同位置、時間重用的物理取樣器啟用；一般有狀態回呼保持原語意。一般成功步的底層速度取樣由五次降至四次，軌跡、事件、QC 與亂數必須一致；呼叫減少比例不是整體加速比例。 |
| 3 | 全案共同前處理與靜態幾何重用 | 同步採用第二工作線的表面稀疏取值改善。正式母體輸入建立並驗收一次，同來源 A 兩站可共用流場與網格；不同站點身分與分母保持獨立。跨次快取必須綁定來源、方法、設定及幾何指紋。 |
| 4 | 編譯可分離的 CPU 數值核心 | OCM 插值、有限水深 Stokes、時間步候選、RK4 最後純量組合與擴散位移使用版本化 Numba 路徑；Python 保留 QC、邊界、事件、亂數抽樣與 RK4 stage 順序。必須在明定誤差內通過 NumPy 參考測試。 |
| 5 | 正式母體固定平行執行 | 依 immutable run plan 的原順序建立連續分組，由固定長壽命 worker 各用同一 controller 接續分片，以重用流場月份窗與程序內 JIT。CPU affinity、獨立 log、失敗停派、checkpoint 與最終完整 validator 都要留下證據。 |

每個 worker 限於單一 run；各程序有自己的資料窗，不宣稱所有程序共享一份 Python 記憶體。不同 ABCD 產品仍需分別讀取；「讀一次」的可實作目標是共用準備成果、重用同程序已開啟資料，以及減少相同來源的重複作業。不同材質、位置、深度與亂數成員仍須各自積分。

### 目前已實作範圍

- `lbt run-worker` 接受同 run 的明確分片清單，先驗證全部 ID，再以同一 controller 依序執行；遇暫停或例外停止。`run-formal-parallel` 再以固定分組啟動多個這類長壽命 worker，任何子程序失敗即停止後續派發；只有所有分片與最後 `validate-run --require-complete` 同時通過才標示完成。詳細參數見 [CLI 參考](cli_reference.md)。
- `ManagedForcingProvider` 明示同點樣本可重用，粒子引擎只在首次正常 RK4 嘗試沿用步首樣本；步長折半與海面階段反射重試仍重新查詢 k1。一般有狀態取樣函式保持原呼叫語意。重用樣本不寫入 checkpoint，不新增跨粒子快取。
- `_surface_series_for_location` 先擷取必要的多維座標，再轉為雙精度，保留原始時間／空間支援與數值語意；不縮小正式輸入的母體範圍。
- `execution.ocm_interpolation_backend` 可明示 `numpy_v1` 或 `numba_ocm_v1`；`execution.physics_kernel_backend` 可明示 `numpy_v1` 或 `numba_cpu_v1`。後者編譯有限水深色散／Stokes 公式、時間步候選、RK4 最後純量組合／時間更新，以及使用既有預抽常態數的擴散位移。Python 仍決定 NWW3／OCM 品質檢查、缺值、邊界、事件、四個 RK4 stage、粒子狀態與每粒子亂數抽樣順序。兩個後端 token 都進入新 run 的設定身分；舊設定省略欄位時仍沿用 NumPy 並維持既有 hash。
- `run-formal-parallel` 在任何 worker 前驗證完整 formal plan、設定 hash、乾淨程式 provenance、checkpoint、forcing 根與 NFS storage gate；本次實際 `scratch_root` 還會以 `findmnt` 即時核對為同一 NFS source，避免把其他掛載點的 PASS 快照誤用。Numba dispatcher 使用 `cache=False`，每個正式 worker 只在自己的長壽命程序內暖機一次，不宣稱跨程序磁碟快取。

持續 worker 的快取計數以每次分片執行前的計數為基準，記錄本次增加的載入、命中、未命中及淘汰次數；同一分片續跑時才與該分片先前已保存的增量累計。多次 checkpoint 只是同一執行區間的進度快照，不可把這些快照再次相加。`manager_count` 與 `resident_bytes` 為狀態量，分片及報告採已觀測樣本的最大值，不是各 worker 同時使用量的總和，也不是連續量測的整機峰值。歷史未標示計數語意的紀錄不能反推精確增量，須保留可讀性並明示其限制，不能將累計快取次數當成已驗證的全案總量。

以上是可供正式母體採用的本地工程候選；尚未因此解除完整共同輸入、逐 RK4 階段 forcing
支援、恢復連續性與科學驗證等正式發布閘門，也尚未在 SERVER 啟動任何正式母體。未來建立
新 formal config 時必須明示兩個 Numba backend，並由實際 run plan 決定母體與分片，不回頭
補做歷史單站倍率比較。A 區既有 1 天、20 情境產物只屬 `engineering_only` DEMO，不能作為
30 天或完整母體的效能、資料支援及科學成果證據。

## 第二工作線：單站小試跑

| 順序 | 改善項目 | 目的與驗收 |
|---|---|---|
| 1 | 表面資料先取少數支援點再轉成雙精度 | 避免為少數點轉換整張網格；保留四角遮罩、有限值、最近點數值、UTC 重複時刻優先序與完整形狀檢核。這也縮短正式全案準備。 |
| 2 | 直接使用仍有效的共同輸入成果 | 到達時刻、來源與幾何未改變時，試跑從已驗收母體選取所需情境，不重建全部母體；任一依賴改變則重新驗證或重建。 |
| 3 | 獨立單站／時間窗建置契約 | 指定新的站點或時窗時，只準備所需資料，並使用明確的工程試跑身分與計數；不得假裝具備完整 100 受體、250 到達時間及 5,000 配對。此項需配套輸入 validator，現有完整母體建置介面不能直接刪除其他站資料。 |

小試跑須分開報告準備、前置驗證、積分、checkpoint 與輸出時間。小試跑加速不能替代正式研究全矩陣的效能驗收。

## 30 天回溯與期限驗收

### 已確認的通用化範圍（2026-09-11）

使用者已確認七天與三十天比較共用通過三十天檢查的到達時刻，並要求回溯天數通用參數化，不建立僅限 7／30／60 的選項清單。實作採用兩個不同意義的參數：`inputs.backtrack_support_days` 是共同輸入要篩選與驗證的正整日上限；`boundaries.max_backtrack_days` 是本次粒子執行的回溯長度。前者只是要求，必須由輸入來源、到達時刻與完整時窗證據驗證，不能因設定已填值就視為資料通過。

本組比較先建一套三十天共同輸入，再由相同母體產生七天與三十天執行設定。兩者共用相同 `design_version`、受體、到達時刻、初始條件、情境 ID 及不可覆寫的輸入檔案；回溯天數改變會形成不同執行設定雜湊、run、checkpoint 與輸出目錄。每份執行設定仍需各自的輕量 runtime preflight inventory，不能混用另一份設定的執行清單。

新增更長回溯時修改參數並重新驗證相應輸入上限即可，不修改程式常數。若超出原母體支援上限，程式必須拒絕直接執行；另建更長支援母體時須明示新版本，檢查是否仍能保留原到達時刻及 48+2 分層。共同日期不足時不減少每站五十筆、不臨時補缺值，也不把不同到達日期的結果視為只有回溯天數不同的比較。

驗收條件包括：非預列天數也能處理、七天／三十天共用母體雜湊與情境身分、超額要求被拒絕、篡改時窗／節點數／到達身分／缺時聲明被拒絕，以及舊設定未宣告新欄位時原設定雜湊不變。新契約不解除 A 區共同 forcing 支援與其他正式發布條件。

通用化透過新欄位與版本化輸入契約擴充，舊七日產品保留原身分。30 天並非方法的理論限制，但每個到達時刻都必須具備往前 30 天的連續時間支撐、實際空間遮罩及必要垂向支援。完整逐小時時間軸含首尾共 721 節點，還須滿足實際查詢的插值支撐。若保留 `2024-01-02T01:00:00Z`，需要自 `2023-12-03T01:00:00Z` 起的資料，不能僅修改 horizon 或以缺值填補。依核定外層邊界合法終止的粒子不必強行存活 30 天，但須與達到回溯上限、資料缺口及數值失敗分別統計。

SERVER 正式啟動前依下列順序驗收；不以新舊版本倍率比較作為目的：

1. 保存候選程式指紋、正式設定／來源／情境／種子，固定成員數、步長與自適應閾值、輸出間隔及終止規則。NumPy 參考與 Numba 的解析、QC、事件及亂數連續性驗證仍是科學正確性閘門；這不是效能倍率測試，也不能事後放寬誤差界線。
2. 確認正式設定明示 `numba_ocm_v1` 與 `numba_cpu_v1`，run plan 涵蓋核准的完整母體，並通過版本化輸入、A 區 `runtime_stage_fail_closed_no_expansion_v1` 空間支援契約、乾淨 deployment provenance、NFS storage 與 checkpoint／RNG 恢復驗證。
3. 依 SERVER 實際 cpuset 與排程核准值設定固定 worker 數；`run-formal-parallel` 記錄整機經過時間、CPU affinity、各子程序狀態、log 與最終完整性，這些是資源與操作證據，不是舊版／新版倍率比較。
4. 執行期間分開保存達到 horizon、資料缺口、數值失敗與邊界終止狀態；任何 child 失敗或訊號中斷先保存 checkpoint 並停止，經 reconcile 與唯讀 validator 後才能明示 `--resume`。
5. 全部 shard、輸出 checksum、QC、資源摘要與 `validate-run --require-complete` 通過後，才能進入聚合、圖表與研究報告；不得以工作執行中或局部區域完成冒充正式成果。

效能工程、任意回溯長度的資料契約、逐階段 forcing 空間支援、科學驗證及報告完成是不同
驗收項目。本文件不解除其他既有正式發布阻擋，也不代表已部署 SERVER 或已完成任一區正式母體。
