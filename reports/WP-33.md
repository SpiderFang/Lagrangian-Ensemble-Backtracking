# WP-33 報告：放寬 `ocm_month_yyyymm` 月份 gate 以與 canonical 去重政策相容

## 1. 問題回顧

`manifests.py` 的 `receptor_arrival_initial_condition` cross-reference gate 原本要求
`ocm_month_yyyymm` 必須嚴格等於 arrival UTC 月份。但 OCM native 月目錄在邊界重疊，
canonical 時間軸 `sort_and_deduplicate_prefer_last` 政策對重複 UTC 一律取最後一個
chunk（較晚的月份），使 `input_derivation.py` 誠實記錄的來源月份可能是 arrival UTC
月份的下一個月；反之若某小時只存在於前一個月目錄，來源月份也可能是上一個月。這兩種
情況都不是資料錯誤，但原本的等號 gate 會把它們擋下——正式建置已因此在 40/5,000 筆
（2025-06-30 兩個時刻 × 20 個南灣受體）上實際失敗過一次。

## 2. 改了什麼

### 2.1 `src/lagrangian_backtracking/manifests.py`

- 新增私有輔助函式 `_shifted_yyyymm(year, month, offset)`（緊接在 `_utc_datetime` 之後，
  約第 1133–1143 行）：以月序號整數加減再還原成 `YYYYMM`，正確處理跨年進位／借位。
  這是本檔案內自成一體的小工具，**沒有**去 import `forcing_window.py` 裡功能相同的
  `_adjacent_month_id`（那是該模組的私有函式，跨模組 import 私有名稱會建立不必要的耦合，
  且不在本次規格允許改動的範圍內）。
- 把原本的等號 gate（約原第 2378–2380 行，現已因新增輔助函式與註解而位移）：

  ```python
  utc = _utc_datetime(time_ns, f"{label}.time_utc_ns")
  if month != f"{utc.year:04d}{utc.month:02d}":
      raise ValueError(f"{label}.ocm_month_yyyymm 與 arrival UTC 月份不一致")
  ```

  改成接受 arrival UTC 月份、前一個月、後一個月（含跨年）三者之一，其餘一律拒絕：

  ```python
  accepted_months = (
      _shifted_yyyymm(utc.year, utc.month, -1),
      f"{utc.year:04d}{utc.month:02d}",
      _shifted_yyyymm(utc.year, utc.month, 1),
  )
  if month not in accepted_months:
      raise ValueError(
          f"{label}.ocm_month_yyyymm 必須是 arrival UTC 月份或其相鄰月份（"
          f"接受 {accepted_months}），實際收到 {month!r}"
      )
  ```

  並在該段落加了中文註解，說明放寬理由（OCM 月目錄邊界重疊、
  `sort_and_deduplicate_prefer_last` 政策、原 gate 在月初邊界無法被滿足）。
- `YYYYMM` 格式檢查（`re.fullmatch(r"[0-9]{6}", month)`）完全保留，沒有動。
- 沒有改 `sort_and_deduplicate_prefer_last`（`time_axis.py`）、沒有改
  `input_derivation.py` 產生端的月份選擇邏輯，符合規格「不能改別處」的限制。

### 2.2 放寬前後的 gate 行為對照

| 情境 | 舊 gate | 新 gate |
|---|---|---|
| `ocm_month_yyyymm` == arrival UTC 月份 | 通過 | 通過 |
| `ocm_month_yyyymm` == arrival UTC 月份的下一個月（重疊窗、prefer-last 取到晚一個月） | **拒絕**（正式建置實際爆掉的情境） | 通過 |
| `ocm_month_yyyymm` == arrival UTC 月份的前一個月（該小時只存在於前一個月目錄） | 拒絕 | 通過 |
| 相差兩個月或以上 | 拒絕（訊息不含接受清單） | 拒絕（fail-closed，訊息列出三個接受值與實際收到值） |
| 跨年邊界（例如 UTC=202401，測 202312／202311） | 202312 也會被拒絕（跨年加減若用天真算法還可能算錯） | 202312 通過、202311 拒絕，跨年月序計算正確 |

## 3. 新增測試（`tests/test_manifests.py`）

在既有 `test_dynamic_initial_condition_rejects_source_and_wetdry_contract` 之後、
`test_dynamic_initial_condition_rejects_physical_and_bracket_corruption` 之前插入五個
新測試函式，全部沿用 `_pilot_dynamic_fixture`（gongliao 站唯一 receptor×arrival pair 的
arrival UTC 固定為 2024-01-01T00:00Z，即 UTC 月份 `202401`）：

1. `test_dynamic_initial_condition_accepts_arrival_utc_month`——`ocm_month_yyyymm="202401"`
   （等於 arrival UTC 月份）必須通過（回歸）。
2. `test_dynamic_initial_condition_accepts_next_month_from_overlap_chunk`——
   `ocm_month_yyyymm="202402"`（下一個月，對應正式建置實際爆掉的
   2025-06-30T01:00Z／`202507` 情境）必須通過。
3. `test_dynamic_initial_condition_accepts_previous_month_from_overlap_chunk`——
   `ocm_month_yyyymm="202312"`（前一個月）必須通過。
4. `test_dynamic_initial_condition_rejects_two_months_away`——
   `ocm_month_yyyymm="202403"`（相差兩個月）仍須拒絕，且以
   `pytest.raises(ValueError, match=r"接受 \('202312', '202401', '202402'\)")`
   驗證錯誤訊息含接受清單。
5. `test_dynamic_initial_condition_month_gate_handles_year_boundary`——跨年邊界：
   UTC 月份 `202401` 時接受 `202312`、拒絕更早一個月的 `202311`。

**與規格第 3 節例子的差異**：規格第 5 項舉例用「UTC=202501 時接受 202412、拒絕
202411」。本檔 fixture（`_pilot_dynamic_fixture`／`_arrival_payload(per_site=1)`）唯一
可用的、且不破壞 `time_utc_ns` 與 arrival 交叉核對的 arrival UTC 是 `2024-01-01`，所以
測試改用 UTC=202401、接受 202312、拒絕 202311——年份不同，但同樣跨年、同樣驗證
`_shifted_yyyymm` 的月序整數加減借位邏輯，功能等價。若需要精確重現規格文字上的
202501/202412/202411，需另外建一個不依賴既有 fixture helper 的最小 receptor/arrival
manifest（因為 loader 會核對 `time_utc_ns` 必須等於已載入 arrival 的實際時間，不能只改
`ocm_month_yyyymm` 而自由改 `time_utc_ns`），評估後認為沒有必要，故未做。
