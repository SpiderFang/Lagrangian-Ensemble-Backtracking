## 2. 問題剖析（完整數字）

### 2.1 症狀

正式版設定為 H90、`M=10`、500,000 顆粒子、197 個工作單元（segment）、54 個 worker
平行執行；主代理在伺服器上實際開跑後，約 25 分鐘全部因記憶體不足（OOM）被系統殺掉。

### 2.2 主代理在伺服器上量到的既有數字（直接引用，未重新量測）

以下數字由主代理在正式伺服器環境上針對單一分段（segment）量測匿名記憶體
（anonymous memory）得出：

| 分段 | 活動粒子數 | 啟動峰值 | 穩態 |
|---|---|---|---|
| 東北（A 區） | 4,000 顆 | 21.8 GB | 7.2 GB |
| 新竹（B 區） | 2,000 顆 | 2.7 GB | 1.8 GB |
| 東北（A 區，`M=1` 對照） | 400 顆 | 1.4 GB（無尖峰） | 1.4 GB |

關鍵訊號：**同一個 A 分段**，`M=10`（4,000 顆活動粒子）啟動峰值高達 21.8 GB，而
`M=1`（400 顆活動粒子，粒子數少 10 倍）完全沒有尖峰、只有 1.4 GB——這個「峰值隨活動
粒子數量級變化」的模式，正是根因定位到 `estimate_substep_count_local_cfl` 內
`cKDTree.query_ball_point` 一次整批查詢的直接證據（見下一節機制說明）。此外「跑滿全程後
穩態仍然膨脹」（A 區穩態 7.2 GB，仍遠高於 `M=1` 的 1.4 GB）顯示這不只是單次尖峰配置的
問題，還有 glibc malloc arena 沒有把释放的記憶體歸還作業系統、隨小時數逐步累積的效應。

### 2.3 機制：為什麼「整批查詢」的尖峰記憶體跟活動粒子數成正比

修正前的寫法（見本次修正的 git diff，`estimate_substep_count_local_cfl` 原本直接做）：

```python
neighbor_lists = spatial_index.element_centroid_kdtree.query_ball_point(points, r=query_radius)
nearby_elements: set[int] = set()
for neighbors in neighbor_lists:
    nearby_elements.update(neighbors)
```

`points` 是**全部**活動粒子的 `(n, 2)` 座標陣列一次整批傳入。scipy 的
`cKDTree.query_ball_point` 對批次輸入的實作，會先幫**每一顆**粒子各自算出一個獨立的
Python `list`（該粒子查詢半徑內的元素索引），再把 `n` 個這種 list 一次全部裝進一個
`dtype=object` 的回傳陣列——**在函式回傳之前，這 `n` 份 list 全部同時存活在記憶體裡**。

查詢半徑是 `radius_safety_factor * 全域最大流速 * 3600 秒 + element_max_reach_m`（見
`estimate_substep_count_local_cfl` 呼叫端 docstring）。在近岸精細網格＋正常量級流速下，
這個半徑足以涵蓋網格一大部分甚至全部元素，單一活動粒子的鄰近元素 list 本身就可能有
數千到數萬個元素。`n` 顆活動粒子的 list 同時存活，總記憶體量是「單顆粒子的鄰近元素數」
乘以「活動粒子數」——因此**尖峰記憶體與活動粒子數成正比**。這正是 2.2 節「A 區
`M=10`（4,000 顆）21.8 GB 尖峰 vs. `M=1`（400 顆）無尖峰、只有 1.4 GB」這個對照的根本
原因。啟動尖峰（約每顆粒子 5.5 MB 暫時配置）與跑滿全程後 glibc malloc arena 未完全歸還、
逐小時累積的穩態膨脹（約每顆粒子 1.6 MB）共同指向同一行程式碼——`tracemalloc`／
`resource.getrusage` 的直接量測（主代理在容器內對合成規模重現此現象時做的初步定位；
完整正式規模的逐行 profiling 未在本報告涵蓋範圍內）都精確指到
`cKDTree.query_ball_point` 這一行。

## 3. 修法原理

修正把 `query_ball_point` 的呼叫從「一次整批查詢」改成
`_query_nearby_elements_chunked`：把 `points` 切成每批最多
`_LOCAL_CFL_QUERY_CHUNK_SIZE`（`32`）顆粒子的小批次，逐批呼叫 `query_ball_point`，把這
一批的結果併入 `nearby_elements` 集合後**立刻捨棄這一批的暫時 list**，讓 Python 的
參照計數在下一批查詢前就把記憶體還給配置器。

原理：`query_ball_point` 批次查詢的記憶體代價，跟「這一次呼叫傳入的粒子數」成正比，
跟「這次呼叫之外還有多少顆粒子等著查」無關——只要每次呼叫的批次夠小，這次呼叫結束、
把結果併入集合、捨棄暫時 list 之後，記憶體就還給配置器，下一批查詢重新開始累積。所以
把 `n` 顆粒子切成 `n / 32` 次呼叫，任何一個時間點同時存活的暫時 list，只對應
**這一個小批次（至多 32 顆）**的鄰近元素數，而不是全部 `n` 顆——尖峰記憶體因此從
「與活動粒子數成正比」降到「與一個小批次的鄰近元素數成正比，跟活動粒子總數無關」。

`_query_nearby_elements_chunked` 額外做了一個提早結束的最佳化：一旦目前累積的
`nearby_elements` 已經涵蓋網格全部元素（`len(nearby_elements) >= total_elements`），
後續批次不可能再貢獻新的元素索引，直接 `break`——這只影響耗時，不影響最終集合內容
（因為集合已經是全域元素集合的上界，繼續查也不會變大）。

## 4. 位元相同與記憶體比較章節（論證與測試證據）

### 4.1 論證

對同一個 `(x, y)` 座標與同一個 `query_radius`，scipy 的 KD-tree 搜尋是純粹依座標與
半徑決定的確定性演算法：同一顆粒子不論是單獨查詢、還是跟其他粒子一起整批查詢，查到的
鄰近元素索引集合必然相同（不同粒子之間的查詢互相獨立，沒有互相影響的邏輯）。因此把
查詢切成多個批次，最終聯集出的 `nearby_elements` 集合，與「一次查完全部粒子」完全相同
——差別只在於「這個集合是分好幾次併起來的，還是一次併起來的」，集合本身的內容不變。

`_query_nearby_elements_chunked` 的回傳值只會被拿去算 `np.min`／`np.unique`／`np.max`
（見 `estimate_substep_count_local_cfl` 呼叫端），這三個運算都只跟輸入陣列的**元素集合
內容**有關、跟元素順序無關。所以就算不同批次大小、不同 Python `set` 疊代順序，最終算出
的 `local_min_edge_length`／`local_max_speed`／`ndeltp` 仍然逐位元相同。

驗收這個論證的測試在 `tests/test_native_hour_major.py`（**不是**
`tests/test_native_backward_driver.py`——這是本次 WP-36 更正的錯誤交叉引用，見第 6 節）：

- `test_estimate_substep_count_local_cfl_chunked_query_matches_unchunked_bit_identical`：

  把 `estimate_substep_count_local_cfl`（分批版）的結果，跟直接照抄修正前邏輯、一次整批

用跟 `tests/test_native_hour_major.py` 的 `driver_grid_memory_probe` fixture 相同邏輯

| 活動粒子數 | 修正前（整批查詢）尖峰 | 修正後（chunk=32）尖峰 |

| 500 | 150.33 MB | 10.23 MB |

| 6,000 | **這個容器的 Python 行程被 OOM killer 直接砍掉（`Killed`，exit code 137）** | 10.23 MB |

599 MB，約 4 倍）、增加到某個粒子數後在資源受限的環境下直接 OOM；修正後（chunk=32）
不論粒子數多少，尖峰都固定在同一量級（三個粒子數量級下都是 10.23 MB，完全沒有隨粒子
數變化）。6,000 顆時修正前版本直接被容器的 OOM killer 砍掉，某種意義上是在這個小規模
合成環境裡重現了伺服器正式規模的 OOM 症狀本身，是相當有力的旁證，但**這不是伺服器正式
規模的量測，不能當成「伺服器端已驗證」的證據**——見第 1 節誠信聲明。

## 6. `_LOCAL_CFL_QUERY_CHUNK_SIZE = 32` 的取捨說明

`_LOCAL_CFL_QUERY_CHUNK_SIZE` 太大，尖峰記憶體會退化回接近原本整批查詢的量級（極端情況
`chunk_size >= n_points` 就完全等於修正前的行為）；太小則 Python 層迴圈呼叫次數變多，
每次呼叫的固定開銷（scipy C 擴充呼叫邊界、`set.update` 的 Python 迴圈）會墊高總耗時。
`32` 是前一輪子代理選定的經驗值，本報告沒有找到（也沒有被要求提供）一組完整的
「不同 chunk size 下耗時 vs. 尖峰記憶體」掃描數據來證明 32 是最佳值；**WP-36 沒有改動
這個常數的值**，只是把描述它的 docstring 文字修正到跟程式碼實際的 32 一致（原文字誤寫
成「128」，這是文字敘述跟程式碼的內部不一致，不是常數本身錯誤，見第 7 節）。若未來正式
規模的量測顯示這個值需要調整，因為第 4 節的位元相同性論證跟 chunk size 無關，只需要改
這一個常數，不影響任何數值結果。
