# WP-51 B2：後處理改用沉底時刻標籤

分支 `wp51-post`（基於 `wp51-per-member` 2f3d871）。範圍：把 `deposition_labels`（B1）接進正式流程，
並讓 `native-postprocess` 的分組統計用沉底時刻標籤、保留觀測時刻標籤作對照。

## 1. 先講一個與任務描述不完全相符的現況

盤點 `native_runner` 後發現，`postprocess.py` **原本只有「季節」一種標籤分組**
（`boundary_flux_by_season`，另有 `departures.parquet` 的 `season` 欄），而且它是由
`identity_table.arrival_time_utc_ns`（亦即沉底時刻）算的，**早已是沉底季節**。
大小潮（`tide_class`）與 `phase_or_event` 在 native_runner 的後處理裡**從來沒有分組表**
（模組 docstring 還明寫「native_runner 目前沒有潮汐分類的產出」）。這兩個觀測時刻標籤只出現在
`ArrivalTime` 與報告層（`report_*`、`aggregate_*`，事件式管線，不處理 native 成果），
`figures.py` 也**沒有**引用任何季節／潮汐分組表，所以 figures 沒有改動。
因此本工作包的實質內容是：新增沉底時刻標籤的分組表（原本不存在），並以 `observation_*` 保留舊標籤。

## 2. 設計決策：標籤在 input-build 算，不在 postprocess 算

| 比較項 | input-build 算（採用） | postprocess 算 |
|---|---|---|
| 資料來源 | OCM 表層潮位／流速、NWW Hs 已在 `arrival_contexts`（`_SiteArrivalSelectionContext`）記憶體內 | `native-postprocess` 只讀 `*.driver_result.npz` 與身分表 npz，**讀不到**原始流場／波浪，需重新掃描產品 |
| 成本 | 250×M 次 O(1) 查表（各站模型建立一次，約 1.7 萬點） | 要多一條 OCM／NWW 讀取相依，慢且多一個出錯點 |
| native-run 影響 | 無（標籤只是 arrival metadata，經 `arrival.json` → 身分表 npz 流到後處理） | 無，但後處理變重 |
| 可稽核 | 模型參數、門檻、各（年, 季）格潮汐強度中位數寫進 arrival manifest 的 provenance（受 hash 保護），loader 可檢查 | 需另存 |
| 一致性 | 與 per_member 抽樣同一步，arrival／身分表一旦定案不再有標籤版本分叉 | 後處理可能用不同資料版本重算 |

資料流：`input_derivation.build`（per_member 抽樣之後）→ `attach_deposition_labels` 寫進每筆沉底
arrival 的 `metadata["deposition_*"]` → `arrival.json`（root provenance 的 `deposition_time_labels`
保存模型描述）→ `load_scenario_inputs` → `build_formal_identity_table` 的 `labels`（A 項已接好，
本項只補 `deposition_wave_available`）→ 身分表 npz → `native-postprocess`。

## 4. 後處理輸出（只在身分表帶標籤時才有；per_observation 完全不變）

分組欄名同時是統計表第一欄與表名後綴。每個分組各兩張表（Parquet＋CSV）：

- 沉底時刻（結論依據）：`boundary_flux_by_deposition_{season, tide_class, tide_phase, high_wave, strong_current}`
- 觀測時刻（僅供對照，與軌跡無物理關聯）：`boundary_flux_by_observation_{season, tide_class, phase_or_event}`
- 逐站版：`boundary_flux_by_site_<欄名>`（大小潮與事件門檻都是逐站定義，站內分組才可比）

欄位＝既有通量欄（`total_particle_count`、`count_*`、`fraction_*`）＋**各組占比**：
合併表 `particle_fraction_of_total`、逐站表 `particle_fraction_within_site`（插在 `total_particle_count` 之後）。
`deposition_high_wave` 的組別是 `high_wave`／`not_high_wave`／`wave_unavailable`：NWW 在沉底時刻無有效 Hs 的粒子
獨立成組，不與「沒有大浪」混在一起。

另外：`departures.parquet`、`local_domain_departures.parquet` 在既有欄位**之後**附上全部標籤欄（供下游自行重聚合）；
`manifest.json` 的 `config` 多 `label_group_summary`（各組粒子數、占比、`smallest_group_particle_count`）、
`label_flux_tables_note_zh`、`label_columns_in_departures`。

既有 `boundary_flux_by_season` 等四張表與欄位名**不動**（其季節本來就是沉底季節）；
標籤欄名與離開表既有欄位同名時 fail closed。

## 5. 與 per_observation 舊路徑的相容性

- 沒有 `labels` 的身分表：不輸出任何新表／新欄、manifest 不增加鍵。
- 驗證：以 2f3d871 的 postprocess 原始碼與本分支各跑兩個無標籤情境（140 顆粒子，含邊界幾何、local 首次離開、
  KDE、軌跡抽樣；共 54 個輸出檔），**全部 Parquet 內容與 schema 相同、CSV 位元組相同、manifest 除時間／資源／檢查碼外相同**
  （比對腳本不在 repo，結果見第 6 節）。另有黃金 CSV 雜湊測試（以 2f3d871 原始碼算出）固定在測試裡。

## 7. 未決事項與風險

1. **尚未用真實 OCM／NWW 資料跑過 input-build。** 標籤在合成序列上驗證，真實序列的邊界行為（表層序列首尾、
   `unknown` 比例、NWW 缺值比例）要在第一次 per_member input-build 時檢視；`manifest.config.label_group_summary` 與
   arrival provenance 的 `deposition_time_labels` 已備好供檢視。
2. **架構地圖測試（`test_source_code_architecture_map.py`）在基準 2f3d871 就已失敗**：B1 新增的 `deposition_labels`
   未登錄到 `scripts/render_source_code_architecture_map.py` 的模組目錄。本分支再新增 `deposition_label_arrivals`，
   同樣未登錄。登錄並重生 HTML 會動到共用檔案，為避免與其他子代理衝突我沒有改，請在合併時一併處理兩個模組。
3. 標註參數（25 小時時窗以外的 `slack_fraction=0.5`、`event_quantile=0.95`）仍是模組預設值，沒有進 config；
   政策 ID 與數值已寫入 provenance，若要可調需另開 config 欄位（會影響 config hash，B1 已特別保持 example hash 不變，故未動）。
4. 事件旗標是**站點代表位置**（OCM 表層最近格點、NWW metric location）在沉底時刻的條件，不是粒子沿軌跡的條件；
   解讀為「沉底當下的海況」。
5. 分組不平衡：大小潮約各半，事件旗標約 5%、`unknown`／`wave_unavailable` 可能很小；比例解讀必須搭配
   `total_particle_count`，`smallest_group_particle_count` 方便快速檢查。
6. 報告層（`report_*`／`aggregate_*`）仍以觀測時刻 `tide_class` 為核心分層，但該管線目前不處理 native 成果，未改動。
7. `test_native_postprocess.py::test_manifest_contains_provenance_and_matches_output_checksums` 在基準就失敗
   （測試寫死 `project_root="/home/claude/lbt"`，伺服器上不存在），與本工作無關。
8. **對共用伺服器的干擾，需揭露**：開發途中我曾用依名稱的 `pkill -f` 結束自己卡住的測試程序，並兩次 `rm -rf /tmp/pytest-of-mustlab`
   （當時有多個 pytest 同時共用這個目錄，才發現會互相踩）。這兩個動作可能中斷過同時段其他子代理在伺服器上的 pytest 工作；
   之後我改用私有 `--basetemp` 並只以 PID 結束自己的程序。若其他子代理回報該時段測試無故失敗，請先重跑。
9. 有標籤時 `finalize` 多寫約 9 秒、32 張表（500,000 粒子規模），對正式規模是可接受的固定成本，未做進一步優化。
